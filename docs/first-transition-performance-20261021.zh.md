# 首次切页与过渡性能优化

## 范围

保持现有颜色、尺寸、token、玻璃底栏与过渡方向，保留 Navigator、ChangeNotifier、LibraryState 和按需挂载 Tab 的架构。没有改动 Playra 工程、媒体引擎、房间同步、依赖清单或全局配置。

目标：减少首次切页及返回缓存页面时的 UI 长帧，避免在过渡开始时重建整页列表；继续保证快速反向切换、后台暂停与业务数据刷新。

## 已复现的问题

相同 Android 模拟器 `127.0.0.1:5557`，780×1560 像素、DPR 2，Skia 渲染后端保持不变。

1. 原生 `Flutter.Frame` 记录显示，调试版初次与重复切页都可能出现超过 16.67ms 的 UI 帧。
2. Widget 构建追踪中，一个 56.38ms 的 UI 帧内，LAYOUT 约 51.26ms；其中离开首页时 WatchHome 重建约 14.79ms。
3. `AppShell.select()` 的整壳层 setState 重新创建页面描述。即使 MotionTabs 已缓存 Element，新的 WatchHome/HistoryPage Widget 仍会触发旧页面更新；active 参数改变还把后台暂停与整个首页更新绑在一起。
4. 根路由覆盖状态的依赖注册在整个 AppShell 上，二级页面开合也会重新生成页面描述。

这里的 UI 帧指 FrameTiming.buildDuration，包含构建、布局和提交绘制工作；不是纯 Widget 构造函数耗时。

回归测试先得到 `Expected: empty / Actual: [WatchHome]`，证明切页时确实更新了不必更新的首页。另一个测试复现了缓存轮播恢复后不足完整 6 秒就前进的问题。

## 实现

- Tab 索引用局部 ValueNotifier 更新；LibraryState 的 ListenableBuilder 只在业务数据变化时重新创建页面描述。
- 路由覆盖依赖放在局部导航 builder 中。主内容继续由 MotionTabs 缓存、按需挂载，并控制 Ticker、焦点、点击与语义。
- 首次点击的目标页先离屏完成布局，下一帧再同步提交页面位移与底栏滑块，保留完整的 280ms 动画。这个准备帧不减少布局本身的成本，作用是避免布局耗时占用动画进度。
- 缓存页继续直接切换；准备任务带选择代次，快速连点、点击当前项取消及退出不会被旧回调抢回选择。减少动画模式立即提交，不等待准备帧。
- HomeCarousel 直接响应所在 TickerMode：隐藏时取消计时，恢复后完整等待一轮；保留应用前后台和减少动画规则。
- ShortFeed 将 TickerMode 纳入媒体可见性条件，保持隐藏或被覆盖时停止持有播放页面。
- 不预先挂载全部 Tab，不冻结收藏/历史数据，不通过跳过生命周期工作换取帧耗时下降。

## 测量方法

- `.local/first-transition-perf.cjs` 从当前应用进程的 VM Service 订阅 Flutter.Frame，通过 ADB 点击实际页面；不读取凭据、不写测试收藏/记录、不创建房间。
- Debug 使用实际账户主入口。Profile 使用 `tool/navigation_benchmark.dart`，直接复用 AppShell、页面、主题、中文本地化与既有 preview 片库，隔离登录/网络因素。正常 Profile 入口拒绝本地 HTTP，保留原 HTTPS 安全规则，不为测量放宽校验。基准 APK 不作为正常 App 交付。
- 每次 cold 模式重新启动进程，保留现有账户和本地数据，比较相同首页 → 记录 → 我的 → 首页路径。
- 每轮包含首次访问及两轮重复访问；相同条件重复采样，保留原始帧，分别看 UI 与栅格峰值。
- 旧 APK 保存于 `.local/backup/first-transition-20261021/app-debug-before.apk`，源码备份在同目录相应路径下。
- Widget 构建追踪仅用于定位，不把开启追踪后的耗时与未追踪的采样直接比较。

首次 Profile 构建失败的 JVM 日志记录了原生内存分配失败：当时物理空闲约 135MB、系统提交内存空闲约 33MB。该环境事件单独记录，不认作应用运行时内存泄漏。后续构建使用命令行内存/并发限制，不修改工程的 Gradle 配置。

模拟器和本地开发 API 随后按原实例/仓库启动命令恢复。Profile 对照开始前，构建已结束，避免编译与 UI 测量并行。

最终采样结果、测试状态与逐文件哈希见 `.local/backup/first-transition-20261021/verification.json`。

## 最终结果

### Profile：三个冷进程的首次切换

下表是每次切换的 UI 帧峰值，再对三个进程取中位数；单位 ms，不是输入响应总延迟。

| 页面 | 改造前 | 最终版 |
| --- | ---: | ---: |
| 短剧 | 8.02 | 4.05 |
| 记录 | 11.72 | 6.48 |
| 我的 | 8.08 | 5.28 |
| 返回首页 | 4.12 | 2.44 |

最终版三轮共 655 帧，UI 峰值 7.69ms、栅格峰值 11.873ms，本组普通 Tab 切换没有超过 16.67ms 的帧。快速连续反向点击压力场景中，UI 峰值 6.46ms、栅格峰值 19.47ms，仍有超预算栅格帧。

改造前样本包含较大的宿主负载异常值。进程重启不会清空操作系统或 GPU 缓存，因此不能把全部栅格差异归因于代码，也不将这组采样等同于真机稳定帧率保证。

### 正常调试 App：缓存页切换

实际测试账户、相同三条切换路径；每次进程内取第二/三轮的 UI 峰值，再汇总六个值取中位数。

| 页面 | 改造前 | 最终版 |
| --- | ---: | ---: |
| 记录 | 45.06 | 22.59 |
| 我的 | 26.82 | 11.97 |
| 首页 | 49.30 | 19.82 |

调试版首次进入“我的”仍未观察到稳定改善：三轮峰值中位数 91.56 → 95.98ms；记录页也出现过 218.56ms 异常峰值。首次布局已放到动画计时前执行，但首次等待并未全部消除。JIT、宿主内存和模拟器负载仍是重要影响因素；不能宣称调试版首次切换完全不卡。

### 二级页面

外观页首次进入的 Profile UI 峰值两轮分别为改造前 47.66/3.78ms、最终版 43.14/3.47ms。后续往返通常较快，首次偶发长帧仍保留为未解决项。追加时间线采样未再次捕获同等长帧；运行时 CPU 采样返回 `Profiler is disabled`，没有据此修改现有音频引擎启动架构或加入未经证实的预热逻辑。

### 验收

- 85 项完整测试通过，静态分析无问题。
- 独立预览页重复点击当前底栏项不会重复入栈；主壳层仍可用当前项取消待切换任务。
- 回归覆盖首次准备帧、底栏/页面同步启动、快速连点取消、减少动画、销毁、缓存页数据刷新、轮播恢复、路由反向与滚动状态保留。
- 与上一轮交付比较，20 项现有主题/媒体文件哈希一致；本轮没有修改样式 token、图片或字体。
- 最终安装恢复为 `lib/main.dart` 普通调试入口，使用原本地账户和服务；基准入口仅用于测量。
- 源文件、范围和回退清单位于 `.local/backup/first-transition-20261021/`。

## 验证边界与回退

调试版冷启动包含 JIT 和检查开销，模拟器还包含宿主 GPU 与系统负载影响；不能把一次热缓存数据当作首次切页收益，也不能以模拟器结果承诺真机稳定帧率。

只恢复本轮备份中实际修改的文件即可回退，保留此前页面统一与用户已有未提交改动。构建产物、追踪、失败日志及临时工具均位于 Git 忽略的 `.local` 或既有构建目录。
